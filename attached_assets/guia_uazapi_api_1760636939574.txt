# Plano de arquitetura (resumo sério e direto)

1. **Fonte de verdade = seu DB do Evolution**

   * O painel **só lê/escreve** no seu banco (conversas, mensagens, contatos).
   * Usuário de DB **read-only** para o painel + **proc de escrita** isolado para eventos (outbox).
   * **Tempo-real**: assina mudanças no DB e streama pro front.

2. **Envio de mensagens = uazapi**

   * O painel chama um **Message Service** que empacota e envia via uazapi (texto, mídia, áudio, docs).
   * **Idempotência** (um `track_id`/`message_uuid` por tentativa), **retries exponenciais**, **backoff** se 429/5xx.
   * **Webhooks/SSE do uazapi** entram num **Ingest Service** e atualizam status no DB (sent/delivered/read/fail).

3. **Realtime pro front**

   * Backend abre **WebSocket/SSE** para o browser.
   * Sempre que cair mensagem nova/atualização no DB, publica para os clientes conectados (sala por chatId).

4. **Front (Next.js + React)**

   * **ConversationList** (virtualizada).
   * **MessageThread** (bubbles, status ticks, previews).
   * **Composer** (texto, arquivo, áudio, emoji, mentions).
   * **Header de Chat** (contato, tags, atendente, chatbot on/off).
   * **Side panel** (lead fields, etiquetas, histórico).

## Fluxo de dados (fim a fim)

* **Entrada** (mensagens recebidas do WhatsApp):

  1. uazapi → webhook/SSE → **Ingest Service**
  2. Ingest normaliza payload → grava no **DB Evolution** (tabelas `chats`, `messages`, `contacts`, etc.)
  3. Trigger/CDC → **Realtime Publisher** → WebSocket → Front atualiza a UI.

* **Saída** (mensagens que você envia no painel):

  1. Front → **Message API** (backend) → cria registro em `messages` com `status='pending'` e `track_id`
  2. Message Service → chama uazapi (endpoint de envio conforme tipo)
  3. uazapi responde `200` → marca `status='sent'` (ou aguarda webhook de confirmação)
  4. Webhook de **delivered/read** chega → atualiza DB → notifica front.

## Banco de dados (modelagem mínima sugerida)

> Não vou reinventar seu schema. Só proponho colunas/índices pra performance.

* `chats`

  * `id (pk)`, `jid` (índice único), `title`, `is_group`, `last_message_at (index)`, `unread_count (index)`
* `messages`

  * `id (pk)`, `chat_id (fk index)`, `direction` ('in'|'out'|'system' index),
    `type` ('text'|'image'|'audio'|'document'|'location'|...),
    `body` (texto), `media_url`, `media_mime`, `duration_ms`,
    `uazapi_message_id (unique nullable)`, `track_id (unique)`,
    `status` ('pending'|'sent'|'delivered'|'read'|'failed' index),
    `error_code`, `error_msg`, `created_at (index)`, `updated_at`
* `contacts`

  * `id (pk)`, `jid` (unique index), `name`, `phone_e164 (index)`, `labels (jsonb index)`, `custom_fields (jsonb)`
* `chat_settings` (opcional)

  * `chat_id`, `assignee_user_id`, `bot_enabled`, `priority`, `tags[]`

**Índices vitais**

* `messages (chat_id, created_at desc)` para paginar rápido.
* `messages (status, created_at)` para workers.
* `chats (last_message_at desc)` para a lista.

## Realtime do DB (duas rotas boas)

* **PostgreSQL**: `LISTEN/NOTIFY` + triggers em `messages` e `chats`.
  Alternativa premium: **logical decoding/pgoutput** ou **Wal2Json** (CDC).
* **MongoDB**: **Change Streams** em `messages` e `chats`.

Se por algum motivo o provedor não permitir, **polling incremental** por `updated_at` com etag de cursor (não é o ideal, mas funciona).

## Backend (Node/TypeScript – sketch)

### 1) Conexão DB + canal realtime

```ts
// db.ts
import { Pool } from 'pg';
export const pool = new Pool({ connectionString: process.env.DB_URL });

// realtime.ts
import WebSocket, { WebSocketServer } from 'ws';
export const wss = new WebSocketServer({ noServer: true });

type Rooms = Map<string, Set<WebSocket>>;
const rooms: Rooms = new Map();

export function joinRoom(ws: WebSocket, roomId: string) {
  if (!rooms.has(roomId)) rooms.set(roomId, new Set());
  rooms.get(roomId)!.add(ws);
  ws.on('close', () => rooms.get(roomId)!.delete(ws));
}

export function publish(roomId: string, event: any) {
  rooms.get(roomId)?.forEach(ws => ws.readyState === ws.OPEN && ws.send(JSON.stringify(event)));
}
```

### 2) LISTEN/NOTIFY para mensagens novas

```ts
// pg-listener.ts
import { pool } from './db';
import { publish } from './realtime';

(async () => {
  const client = await pool.connect();
  await client.query('LISTEN messages_inserted');
  await client.query('LISTEN messages_updated');

  client.on('notification', (msg) => {
    const payload = JSON.parse(msg.payload!);
    // payload: { chat_id, message_id, type: 'insert'|'update' }
    publish(`chat:${payload.chat_id}`, { kind: 'message', ...payload });
    if (payload.type === 'insert') publish('inbox', { kind: 'inbox_update', chat_id: payload.chat_id });
  });
})();
```

### 3) Envio via uazapi com idempotência

```ts
// uazapi.ts
import fetch from 'node-fetch';

const BASE = process.env.UAZAPI_BASE;        // ex: https://free.uazapi.com
const SUB  = process.env.UAZAPI_SUBDOMAIN;   // ex: 'free'
const TOKEN= process.env.UAZAPI_TOKEN;

export async function sendText({ number, text, trackId }:{
  number: string; text: string; trackId: string;
}) {
  const url = `${BASE}/message/text`;
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type':'application/json', 'token': TOKEN, 'x-track-id': trackId, 'x-subdomain': SUB },
    body: JSON.stringify({ number, text, track_id: trackId }), // manter um dos headers/campo corpo para idempotência
  });
  if (!res.ok) throw new Error(`uazapi ${res.status}`);
  return res.json();
}
```

### 4) Worker de envio (garante retries e marca status)

```ts
// outbox-worker.ts
import { pool } from './db';
import { sendText } from './uazapi';

const RETRYABLE = new Set([408, 429, 500, 502, 503, 504]);

async function tick() {
  const { rows } = await pool.query(
    `UPDATE messages
       SET status = 'sending'
     WHERE id IN (
       SELECT id FROM messages
        WHERE direction='out' AND status IN ('pending','retry')
        ORDER BY created_at ASC
        FOR UPDATE SKIP LOCKED
        LIMIT 50
     )
     RETURNING id, chat_id, body, track_id, target_jid`
  );

  for (const m of rows) {
    try {
      await sendText({ number: m.target_jid, text: m.body, trackId: m.track_id });
      await pool.query(`UPDATE messages SET status='sent' WHERE id=$1`, [m.id]);
    } catch (e:any) {
      const retry = RETRYABLE.has(Number(e.message.split(' ')[1]));
      await pool.query(
        `UPDATE messages SET status=$2, error_msg=$3 WHERE id=$1`,
        [m.id, retry ? 'retry' : 'failed', String(e.message).slice(0, 500)]
      );
    }
  }
}

setInterval(tick, 1500);
```

### 5) Webhook de status (delivered/read/failed)

```ts
// webhook.ts (Express)
app.post('/webhooks/uazapi', async (req, res) => {
  const ev = req.body; // normalizar conforme payload real
  // mapear ev.message_id / track_id -> message.id
  await pool.query(
    `UPDATE messages
        SET status=$2, uazapi_message_id=COALESCE(uazapi_message_id, $3), updated_at=NOW()
      WHERE track_id=$1`,
    [ev.track_id, ev.status, ev.message_id]
  );
  res.sendStatus(200);
});
```

## Frontend (Next.js/React – sketch)

## Tipos de mensagem suportados (módulos de envio)

Crie um adapter por tipo:

* **Texto**: `sendText({ number, text, trackId })`
* **Imagem**/**Documento**: `sendMedia({ number, url|buffer, filename, caption, trackId })`
* **Áudio (PTT)**: `sendAudio({ number, url|buffer, ptt:true, trackId })`
* **Localização/Contato/Sticker**: adapters específicos
* **Respostas/mentions**: incluir `replyId` (citar mensagem) e `mentions` quando grupo

> Padrão do sistema: **sempre** gerar `track_id` no backend, registrar primeiro no DB (`status='pending'`), e só então chamar uazapi.

## Estados e tolerância a falhas

* **Fila interna** (outbox) com backoff de 1s, 2s, 4s, 8s, máx 1min; depois marca `failed` e deixa botão **Reenviar** no front.
* **Reconexão**: se WebSocket cair, front tenta reconectar e roda um **delta sync** (pega mensagens após o último `updated_at` visto).
* **Rate limit**: se 429, **pausa por N segundos** (header Retry-After, se existir) e aplica backoff global.

## Segurança e operação

* `.env`: `DB_URL` (preferir read-only para leitura), `UAZAPI_BASE`, `UAZAPI_SUBDOMAIN`, `UAZAPI_TOKEN`
* **Tokens**: rotacionar; nunca no front.
* **Logs**: correlação por `track_id`; salvar requestId/traceId.
* **Observabilidade**: métricas por status de envio, latência uazapi, erros por tipo.

## Roadmap de entrega (incremental e seguro)

1. **MVP de leitura:** lista de chats + thread (paginado), sem envio.
2. **Realtime:** habilitar LISTEN/NOTIFY (ou Change Streams) + WebSocket.
3. **Envio texto:** outbox + worker + uazapi + webhook de status.
4. **Mídia/áudio:** upload + envio + previews.
5. **Qualidade de vida:** busca, labels, tags, assignee, bot on/off.
6. **Hardening:** retries finos, métricas, dashboards.
